# 研报 RAG 检索优化实验报告

## 1. 实验目标

针对基础 RAG 系统在研报问答中存在的"具体数据检索不准"和"相似章节容易混淆"等问题，基于 20 份研报和 30 条标注测试集，对检索模块进行优化实验。

本次实验以**向量检索**作为 Baseline，在保持数据集、Chunk 切分方式、Embedding 模型及评估标准一致的前提下，测试两种优化方案：

1. **Hybrid Retrieval + Rerank**：BM25 + 向量检索进行候选召回，再通过 Rerank 重排序；
2. **Query Rewrite**：将原始问题转换为包含行业、章节、时间和关键指标等信息的检索查询，再进行向量检索。

主要通过 Recall@3 和 Recall@5 衡量检索结果是否包含标注的目标研报及目标章节。

---

## 2. 方法说明

### 2.1 Baseline：Vector Retrieval

将 20 份研报按照一级章节切分，共得到 100 个 Chunk。对用户问题进行 Embedding 后，与全部 Chunk 计算 Cosine Similarity，并返回 Top-K 结果。

评估标准为：检索结果同时满足 `relevant_report` 和 `relevant_section`，视为命中。

### 2.2 方案一：Hybrid Retrieval + Rerank

采用 BM25 和向量检索分别召回 Top10，合并去重后形成候选集，再使用 Rerank 模型进行最终排序。

该方案主要解决两个问题：

- BM25 补充行业名称、专业术语等关键词的精确匹配；
- Rerank 对候选结果进行更细粒度的相关性判断。

### 2.3 方案二：Query Rewrite

针对原始问题信息较短、与研报原文表达存在差异的问题，使用 LLM 对 Query 进行检索导向的结构化改写，提取：

- 行业
- 目标章节
- 时间
- 关键指标
- 检索关键词

例如：

> 原问题：化工龙头企业 2024 年的营收和净利润预计是多少？

改写为：

> 化工 + 核心数据 + 2024年 + 营业收入 + 净利润 + 龙头企业 + 预计

随后使用改写后的 Query 进行原有向量检索。

---

## 3. 实验结果

| 方法                     |   Recall@3 |   Recall@5 | 相比 Baseline        |
| ---------------------- | ---------: | ---------: | ------------------ |
| Vector Retrieval       |     60.00% |     66.67% | —                  |
| BM25 + Vector + Rerank | **66.67%** | **76.67%** | +6.67pp / +10.00pp |
| Query Rewrite + Vector |     63.33% |     70.00% | +3.33pp / +3.33pp  |

从整体结果看，两种优化方案均带来一定提升。其中 **Hybrid + Rerank 的提升最明显**，Recall@5 从 66.67% 提升至 76.67%，说明增加关键词召回并进行候选重排序后，能够有效改善部分原始向量检索中的召回和排序问题。

Query Rewrite 也带来一定提升，但幅度较小，且存在部分 Case 退化，说明 Query Rewrite 可以缓解 Query 与文档之间的表达差异，但并不能稳定解决研报之间的相似内容竞争问题。

---

## 4. Case 分析：实验发现的主要问题

结合 Top-K 检索结果进行分析后，当前系统的主要问题并不是单纯的"召回数量不足"，而是**不同研报的相同章节存在较高文本相似度，导致模型难以进一步区分目标行业**。

### Case 1：风险类问题是当前最明显的失败类型

例如：

> "AI 行业有哪些主要风险？"

Query Rewrite 后得到：

> `人工智能 风险提示 主要风险`

虽然 Query 已经明确包含"人工智能"和"风险提示"，但检索结果中仍容易出现其他行业的风险提示章节。

类似情况还出现在军工、钢铁、旅游、快递物流、电力等风险问题中。

原因在于不同研报的风险提示通常具有较强的模板化特征，例如政策风险、市场风险、竞争风险等表达高度相似。

因此，当前模型能够较好识别：

> **这是一个"风险提示"问题**

但对于：

> **"这是哪个行业的风险提示？"**

区分能力仍然不足。

---

### Case 2：核心数据问题存在明显的跨行业竞争

例如：

> "半导体龙头企业 2024 年的营收和净利润预计是多少？"

Baseline 检索结果中，多个其他行业的"核心数据"章节排名靠前，正确的半导体核心数据章节没有进入 Top3。

Query Rewrite 后：

> `半导体 核心数据 2024年 营业收入 净利润 龙头企业 预计`

正确的半导体核心数据章节进入 Top5。

这说明 Query Rewrite 对"**行业 + 时间 + 指标**"类型的问题确实能够提供帮助。

但类似的化工、消费电子等问题仍然会出现多个行业核心数据章节竞争，说明仅增加"营收、净利润、2024年"等语义信息，仍不足以完成精确的行业定位。

---

### Case 3：Query Rewrite 并非稳定有效

Query Rewrite 并不是所有问题都会提升。

例如创新药核心数据问题，Baseline 中正确结果能够进入 Top3，而改写后反而出现排名下降。

这说明：

> **增加更多关键词 ≠ 一定能够提高向量检索效果。**

当多个研报具有相似的章节结构和表达时，加入"核心数据、预计、龙头企业"等通用词，也可能增加不同文档之间的语义重合。

因此，Query Rewrite 更适合解决**查询表达不充分**的问题，而不是解决所有检索错误。

---

## 5. 实验结论

综合实验结果和 Case 分析，可以得到三个关键发现：

**第一，Hybrid + Rerank 是本次实验中提升最明显的优化方案。**
BM25 能够补充向量检索的关键词匹配能力，Rerank 则进一步改善候选结果排序，因此对整体 Recall 有较明显提升。

**第二，Query Rewrite 能改善部分 Query-Document 表达不一致的问题，但提升有限。**
对于包含明确行业、时间、指标的问题，改写能够帮助模型更准确地理解检索意图；但其效果并不稳定。

**第三，也是本次实验最重要的发现：当前系统的主要瓶颈已经从"Query 表达不足"转向"相似章节之间的精确区分"。**

尤其是风险提示和核心数据章节，不同行业的文本结构高度相似。此时即使继续增加 Query 关键词，模型仍可能在多个行业的相似 Chunk 之间产生混淆。

因此，当前问题更接近：

> **语义召回能够找到"正确类型的章节"，但缺少对"正确行业/实体"的强约束。**

---

## 6. 下一步优化建议

基于上述实验发现，下一步不建议继续单纯堆叠 Query Rewrite，而应重点加强**结构化信息约束**。

### 6.1 引入 Metadata Filter / Entity Filter

利用 Chunk 已有的 `report_id`、`section`、报告标题、日期等 Metadata，对 Query 中识别出的行业、章节、时间等信息进行结构化过滤。

例如：

> "半导体龙头企业 2024 年营收和净利润"

可以先识别：

- 行业：半导体
- 章节：核心数据
- 时间：2024 年

再在满足条件的候选范围内进行向量检索和 Rerank。

这能够直接针对当前实验中最明显的**跨行业相似章节误召回**问题。

### 6.2 对行业、公司、时间、指标增加显式匹配

对于行业名称、公司名称、年份、营收、净利润、CR5 等实体和指标，可以增加关键词或实体级匹配，避免完全依赖语义相似度。

最终可以形成：

> **Metadata / Entity Filter → Hybrid Retrieval → Rerank**

的检索链路。

### 6.3 扩充测试集并进行分类型评估

当前测试集仅有 30 条问题，下一步可以扩大测试集，并分别统计：

- 风险提示
- 核心数据
- 竞争格局
- 投资建议
- 评级

等不同问题类型的 Recall。

这样可以进一步验证优化方案究竟改善了哪类问题，并判断后续优化应该优先针对**风险类问题**还是**结构化数据类问题**。

---

## 7. 总结

本次实验表明，**BM25 + Vector + Rerank 能够有效提升基础向量检索的整体 Recall，但进一步分析发现，当前系统的核心瓶颈并非简单的语义召回不足，而是不同研报相同章节之间的高度相似导致的跨行业混淆。**

Query Rewrite 可以改善部分查询表达不充分的问题，但对这一核心瓶颈的解决能力有限。

因此，下一阶段的优化重点应从单纯优化"**Query 怎么表达**"转向优化"**如何利用行业、章节、时间等结构化信息约束检索范围**"，通过 Metadata / Entity Filter 与 Hybrid Retrieval、Rerank 结合，进一步提升研报场景下的精确检索能力。
